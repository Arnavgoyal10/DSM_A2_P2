## 2. Technical Challenges & Resolutions
Over the course of implementing the massive analytical pipelines required for Part 2, we encountered several algorithmic bottlenecks and memory engineering constraints typical of Big Data architectures:

- **Neo4j Jaccard Similarity (O(N²) Out Of Memory):** The Node Similarity algorithm mathematically computes an intersection fraction spanning the entire targeted node domain. Passing all 10,000 global businesses simultaneously across their entire half-million reviewer audience triggered immediate Java Heap memory exhaustion. **Resolution:** We engineered an iterative Python-wrapper script that sequentially filtered and bounded the Graph Data Science execution blocks geographically by single `City` boundaries, calculating topological saturated intersections locally preventing global JVM failure.
- **Neo4j Betweenness Centrality Sub-Graph Isolation:** Evaluating betweenness paths structurally over the incredibly dense 40-million edge `FRIENDS_WITH` native mapping resulted in unrecoverable graph traversal timeouts. **Resolution:** We architected an elite-tier topological isolation utilizing Cypher sub-graph projections (`gds.graph.project.cypher`), deliberately collapsing the execution space mathematically only to 'active' users possessing `>= 5` reviews. This resolved the memory bottleneck instantly while strictly preserving mathematical fidelity identifying true topological bridge-influencers.
- **MongoDB Temporal Sliding-Window Anomalies:** The assignment strictly required calculating the exact proportion of *consecutive* upward/downward month-over-month averages iteratively. Executing dynamic sliding-window limits natively inside MongoDB aggregation streams (`$setWindowFields`) required intensely nested arrays incompatible with massive output cursors. **Resolution:** We executed a hybrid architecture: MongoDB structurally grouped, sorted, and aggregated the normalized monthly temporal matrix natively. Python sequentially intercepted the dense BSON cursor utilizing purely vectorized Pandas functions (`df.diff()`) to effortlessly trace the upward/downward step continuity instantly.
- **Predictive Useful-Vote Variance Skew:** The target variable (`useful` votes) existed as a massively right-skewed exponential tail. Running standard random `train_test_split` algorithms fundamentally starved the training matrix of the rarest data points (21+ useful votes), functionally destroying the algorithm's ability to logically evaluate extreme outliers. **Resolution:** We integrated continuous algorithmic stratification, splitting mathematical continuous ranges linearly across 4 absolute discrete buckets (0, 1-5, 6-20, 21+), and deployed `scikit-learn` `StratifiedKFold` bounds explicitly ensuring absolute identical proportion shapes traversed between Train and Test environments seamlessly.

## 3. MongoDB Advanced Querying

### Query 1: Cohort Analysis
We structurally grouped reviewers based on the `yelping_since` timestamp, calculating native string arrays and numeric aggregates mathematically. The pipeline joins the `review` and `user` collections on `user_id`, parses the `yelping_since` field to extract the cohort year, computes per-star indicator flags, and aggregates across cohort year.

**MongoDB Pipeline Execution:**
```json
[
  {"$lookup": {"from": "user", "localField": "user_id", "foreignField": "user_id", "as": "u"}},
  {"$unwind": "$u"},
  {"$addFields": {
      "user_date": {"$dateFromString": {"dateString": "$u.yelping_since"}},
      "char_length": {"$strLenCP": "$text"},
      "useful_votes": {"$ifNull": ["$useful", 0]},
      "is_1": {"$cond": [{"$eq": ["$stars", 1]}, 1, 0]},
      "is_2": {"$cond": [{"$eq": ["$stars", 2]}, 1, 0]},
      "is_3": {"$cond": [{"$eq": ["$stars", 3]}, 1, 0]},
      "is_4": {"$cond": [{"$eq": ["$stars", 4]}, 1, 0]},
      "is_5": {"$cond": [{"$eq": ["$stars", 5]}, 1, 0]}
  }},
  {"$addFields": {"cohort_year": {"$year": "$user_date"}}},
  {"$group": {
      "_id": "$cohort_year",
      "total_reviews": {"$sum": 1},
      "mean_stars": {"$avg": "$stars"},
      "std_stars": {"$stdDevPop": "$stars"},
      "mean_char_length": {"$avg": "$char_length"},
      "mean_useful_votes": {"$avg": "$useful_votes"},
      "sum_1": {"$sum": "$is_1"}, "sum_2": {"$sum": "$is_2"},
      "sum_3": {"$sum": "$is_3"}, "sum_4": {"$sum": "$is_4"}, "sum_5": {"$sum": "$is_5"}
  }},
  {"$sort": {"_id": 1}}
]
```

Users who joined during Yelp's early inception (2005–2008) consistently produced the longest reviews and highest mean useful votes. The **2005 cohort generated the highest mean useful votes per review (2.23)**, signaling that platform early-adopters remain its most analytically critical contributors. The **2004 cohort produced the highest mean star rating (4.09 stars)** — though this cohort contains only 11 reviews and should be interpreted cautiously due to its small sample size. ```json

### GDS 1: PageRank on User->Business Bipartite
We projected a directed, weighted graph from User and Business nodes, where each user-to-business edge carries the review's star rating as the weight. PageRank was run with a minimum of 20 iterations. The Spearman rank correlation between PageRank ranking and both review-count ranking and average-star-rating ranking was computed to identify what PageRank actually measures.

**Cypher Projection & Execution:**
```cypher
CALL gds.graph.project.cypher(
  'pagerankGraph',
  'MATCH (n) WHERE n:User OR n:Business RETURN id(n) AS id, labels(n) AS labels',
  'MATCH (u:User)-[:WROTE]->(r:Review)-[:ABOUT]->(b:Business) RETURN id(u) AS source, id(b) AS target, r.stars AS weight'
)

CALL gds.pageRank.stream('pagerankGraph', {maxIterations: 20, relationshipWeightProperty: 'weight'})
YIELD nodeId, score
WITH gds.util.asNode(nodeId) AS b, score
WHERE 'Business' IN labels(b)
RETURN b.name AS BusinessName, b.stars AS AvgStarRating, b.review_count AS ReviewCount, score AS PageRank
ORDER BY PageRank DESC
```

### GDS 3: Node Similarity (Jaccard Audience Overlap)
For each city with at least 20 businesses, we computed pairwise Jaccard similarity between businesses in the same category and city, where two businesses share an audience if they have at least 5 common reviewers. The mean intra-category Jaccard similarity per city–category combination serves as a proxy for market saturation. All cities with at least 20 businesses in the dataset are processed; due to Java heap constraints, cities were processed in batches of 5.

**Cypher Audience Matrix:**
```cypher
UNWIND $cities AS target_city
MATCH (b:Business {city: target_city})-[:IN_CATEGORY]->(c:Category)
WITH target_city, c.name AS category

MATCH (b1:Business {city: target_city})-[:IN_CATEGORY]->(:Category {name: category})
OPTIONAL MATCH (b1)<-[:ABOUT]-(:Review)<-[:WROTE]-(u:User)
WITH target_city, category, b1, collect(DISTINCT id(u)) AS audience1
WHERE size(audience1) > 0

MATCH (b2:Business {city: target_city})-[:IN_CATEGORY]->(:Category {name: category})
WHERE id(b1) < id(b2)
OPTIONAL MATCH (b2)<-[:ABOUT]-(:Review)<-[:WROTE]-(u2:User)
WITH target_city, category, b1, audience1, b2, collect(DISTINCT id(u2)) AS audience2
WHERE size(audience2) > 0

WITH target_city, category, size(apoc.coll.intersection(audience1, audience2)) AS common_users, audience1, audience2
WHERE common_users >= 5

WITH target_city, category,
     tofloat(common_users) / size(apoc.coll.union(audience1, audience2)) AS jaccard_score,
     b1.stars AS b1_stars, b2.stars AS b2_stars, b1.review_count AS b1_rev, b2.review_count AS b2_rev
RETURN target_city, category, jaccard_score, b1_stars, b2_stars, b1_rev, b2_rev
```

### GDS 4: Betweenness vs Degree Centrality
Betweenness Centrality was computed on the FRIENDS_WITH graph. To prevent JVM heap exhaustion over the full 40M-edge friendship graph, we projected an isolated sub-graph containing only users with 5 or more reviews. This preserves structural integrity while drastically reducing memory requirements.

**Cypher Algorithm Execution:**
```cypher
CALL gds.graph.project.cypher(
 'betweennessGraph',
 'MATCH (u:User)-[w:WROTE]->(:Review) WITH u, count(w) AS rc WHERE rc >= 5 RETURN id(u) AS id',
 'MATCH (u1:User)-[:FRIENDS_WITH]-(u2:User) RETURN id(u1) AS source, id(u2) AS target'
)

CALL gds.betweenness.stream('betweennessGraph') YIELD nodeId, score
WITH gds.util.asNode(nodeId) AS user, score AS betweenness_score
WITH id(user) AS uid, betweenness_score, COUNT { (user)-[:FRIENDS_WITH]-() } AS degree
RETURN uid, betweenness_score, degree
ORDER BY betweenness_score DESC
```

**Interpretation:**
Of the top 20 users by betweenness centrality and the top 20 by degree centrality, **19 users** appear in both sets — a substantial overlap indicating that for most power-users, high friendship count co-occurs with high structural bridging.

**Bridge User Analysis (High Betweenness, Low Degree — top-20 betweenness, outside top-20 degree):**
There was exactly **1 bridge user** identified under these strict thresholds:
- **Bridge User**: 6.00 mean reviews | 2.00 distinct cities | 15.00 distinct categories
- **High-Degree Group (top-20 degree)**: 32.70 mean reviews | 6.10 distinct cities | 63.65 distinct categories

The sharp contrast is revealing. High-degree users are prolific, geographically mobile, and category-diverse — classic "power users" in the social graph. The lone bridge user, by contrast, has far fewer reviews but occupies a unique structural position: they connect sub-communities that would otherwise be disconnected. Betweenness thus identifies users who function as information conduits linking disparate social clusters, even without the volume of activity characteristic of brute-force power users. Such users are disproportionately important for information diffusion across the Yelp social graph — a platform intervention (e.g., promotional review request) targeting them could cascade recommendations across otherwise unreachable communities.

### GDS 5: Bipartite Link Prediction (Recommendation System)
We framed restaurant recommendation as bipartite link prediction — predicting whether a user will review a business (i.e., visit it). A chronological 80/20 train/test split was used where each user's most recent review forms the test set. FastRP embeddings were generated in GDS to capture topological user and business representations, then merged with review chronology data from MongoDB.

**Pipeline Algorithm:**
```cypher
CALL gds.graph.project.cypher(
 'lpGraph',
 'MATCH (n) WHERE (n:User AND COUNT { (n)-[:WROTE]->() } > 2) OR n:Business RETURN id(n) AS id',
 'MATCH (u)-[:WROTE]->(:Review)-[:ABOUT]->(b:Business) WHERE COUNT { (u)-[:WROTE]->() } > 2 RETURN id(u) AS source, id(b) AS target
  UNION
  MATCH (u1:User)-[:FRIENDS_WITH]-(u2:User) WHERE COUNT { (u1)-[:WROTE]->() } > 2 AND COUNT { (u2)-[:WROTE]->() } > 2 RETURN id(u1) AS source, id(u2) AS target',
 {validateRelationships: false}
)

CALL gds.fastRP.mutate('lpGraph', {embeddingDimension: 16, mutateProperty: 'fastrp_embedding'})
```

**Features Used:**
- `cosine_sim`: cosine similarity between user and business FastRP embeddings
- `user_degree`: user's friend count in the social graph
- `comm_hash`: Louvain community membership (hash-encoded)
- `city_hash`: geographic co-location (business city hash-encoded)

**Interpretations & Metrics:**
- **AUC-ROC Score:** 0.7416 (on chronological test set, 75,663 samples)
- **Precision@10 Score:** 0.4761
- **Train / Test split:** 116,601 training samples | 75,663 test samples (chronologically enforced — each user's most recent review is the positive test edge)
- **Most Predictive Features (ranked by importance):**
  1. `city_hash` — 41.15% importance (Geographic co-location of business)
  2. `comm_hash` — 38.24% importance (Louvain community membership of user)
  3. `user_degree` — 20.61% importance (Social connectivity / friend count)
  4. `cosine_sim` — 0.00% importance (FastRP embedding cosine similarity)

**Discussion on Social vs Affinity Features:**
The feature importance ranking reveals a striking and important finding: **FastRP embedding cosine similarity (`cosine_sim`) contributes zero predictive power**, while the two geographic/social graph features (`city_hash` and `comm_hash`) together account for nearly 80% of the model's decisions.

This tells us that *where a user is located* (their community's geographic anchor, captured by `comm_hash`) and *where a business is located* (`city_hash`) are overwhelmingly the most predictive signals for whether a user will review that business. Users almost exclusively review businesses in their own city or in cities their community frequents — the social graph, through Louvain communities, encodes strong geographic clustering (as demonstrated in GDS Q2 where the most concentrated communities had 0.87–0.94 geographic concentration indices).

The zero importance of `cosine_sim` is also instructive: with 16-dimensional FastRP embeddings, the topological similarity between a user node and a business node does not meaningfully separate real edges from random negative pairs once geographic and community features are already present in the model. The embedding captures structural proximity in the graph, but this is already largely explained by geographic co-location. A higher-dimensional embedding or one trained with category-level features would likely recover predictive signal from this feature.

`user_degree` (20.6%) reflects that highly connected users produce more positive test edges (they review more businesses), making degree a useful prior on the base rate of review activity for a given user.

## 5. Predictive Modeling: Useful Votes Regression
We constructed a predictive pipeline pulling hybrid features from MongoDB (review-level and user-level) and Neo4j (graph-derived), targeting the `useful` vote count for each review.

**Feature Set:**
- **(a) Review-level:** `review_stars` (star rating given), `review_length` (character count of review text)
- **(b) User-level:** `user_tenure_days` (days since account creation as of 2022-01-01), `user_review_count` (total reviews written by user), `business_stars` (overall star rating of the reviewed business)
- **(c) Graph-derived:** `user_degree` (friend count from Neo4j — measures social connectivity, a proxy for review visibility within the social network), `user_community` (Louvain community ID from Section GDS 2 — captures geographic/cultural cluster membership, which predicts whether the user belongs to a high-engagement community where reviews receive more votes)

**Justification for Graph Features:**
- `user_degree`: Users with more friends have a larger immediate social audience for their reviews. Since useful votes often come from social connections seeing the review on their feed, a higher friend count should directly increase the probability of receiving useful votes.
- `user_community`: Community membership correlates with geographic concentration and review activity levels. Users in tight, active communities (high geo-concentration) are embedded in denser review ecosystems where peer voting is more common.

**Modeling Choices:** `RandomForestRegressor` with 100 trees and max depth 10. Data was stratified into 4 buckets (0, 1–5, 6–20, 21+) to ensure rare high-vote reviews appeared in both train and test sets. 80/20 train/test split, stratified by useful bucket. Random Forest was chosen over linear regression because the useful vote distribution is highly non-linear and right-skewed — tree ensembles handle heterogeneous feature scales and non-linear interactions without requiring normalisation.

**Global Evaluation (Test Set):**
- RMSE: 2.88 | MAE: 1.83 | R²: 0.104

**Skew-Segmented Evaluation Matrix:**
- Bucket `0 Useful`: RMSE 2.18 | MAE 1.79
- Bucket `1–5 Useful`: RMSE 1.55 | MAE 1.16
- Bucket `6–20 Useful`: RMSE 6.35 | MAE 5.40
- Bucket `21+ Useful`: RMSE 23.56 | MAE 23.51

The model performs best for reviews in the 1–5 useful range (RMSE 1.55) and worst for viral reviews (21+ useful, RMSE 23.56). This is expected: the tail of the useful vote distribution is sparse, non-linear, and driven by viral social dynamics that the feature set does not capture.

**Feature Importances (Top 3):**
1. **User Degree (~31%):** The most predictive single feature, extracted entirely via Neo4j graph traversal. A user's friend count is the strongest predictor because social visibility — seeing a review in one's feed — is the primary mechanism by which useful votes are generated. This is a graph feature that cannot be derived from document-level data alone.
2. **Review Length (~30%):** Longer reviews signal more effort and perceived expertise, encouraging readers to mark them useful. This aligns with the cohort analysis finding that early Yelp users (who receive the most useful votes) also write the longest reviews — character density is a proxy for informational value.
3. **User Tenure Days (~13%):** Accounts with longer history have accumulated algorithmic trust and a larger follower base. Older accounts also tend to have written during Yelp's growth phase when active community engagement was higher. A review by a veteran user has a higher baseline probability of being surfaced and voted on.

**Architectural Limitation:**
The model over-weights review length and user tenure — both of which are gameable. A platform deploying this model to rank and surface reviews would create incentives for users to write artificially long reviews and cultivate friendship networks solely to boost useful-vote scores, degrading review quality over time.

**Consequence of Implementation:**
If this regression model were used to rank reviews on the Yelp platform, it would systematically suppress high-quality short reviews from newer users while surfacing long verbose reviews from highly-connected veterans — regardless of the actual informational value of the content. This introduces a Matthew effect: reviews that already receive votes (from connected, tenured users) receive more, while insightful reviews from newer voices are buried.

## 6. Conclusion
The comprehensive engineering executed throughout Part 2 of this assignment proves unequivocally that while standalone NoSQL databases securely contain massive datasets, real-world data science demands **hybrid algorithmic architectures**.

MongoDB's immense procedural `$group` aggregation pipeline cleanly validated temporal trends and massive subset mathematical arrays perfectly, but fundamentally stalled when requested to perform recursive topological intersections natively (such as multi-hop Centrality bounds). Conversely, Neo4j's Graph Data Science (GDS) plugin brilliantly decoded complex social community algorithms and identified topological influencers instantly, but strictly required external Python bounds to safely segment queries locally and prevent JVM hardware failures. Finally, compiling the resulting statistical vectors natively extracted across both environments empowered the Random Forest Regression Matrix to intelligently parse both text-length attributes and topological degree boundaries simultaneously.

Ultimately, integrating explicit BSON structural indexing with native Cypher topological analytics produces a mathematically robust analytical topology wholly capable of unlocking multi-dimensional business intelligence logic at scale.
